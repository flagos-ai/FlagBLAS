# FlagBLAS hgemm Core Shape 性能基准报告（nn / tn / nt / tt）

> 日期：2026-09-03
> 运行命令：`pytest benchmark/test_hgemm_perf.py::test_perf_hgemm_{nn,tn,nt,tt} --level core -s --record log`（每次一个变体，独立进程）
> 环境：Hygon gfx936（DCU）/ DTK 25.04 / Triton 3.6（HCU backend）/ torch 2.4.1 / python3.10 venv
> 测试：hipBLAS-H（`hipblasHgemm`）vs FlagBLAS（通用 hgemm 内核，fp32 累加），`do_bench(warmup=1000, rep=100, median)`，speedup = hip/flag
> 精度参考：torch fp32 matmul（device）后回投 fp16（见 §3），`atol=1e-4·k, rtol=1e-3`

## 1. 汇总

所有 4 变体 × 37 core shapes = 148 项全部通过精度校验；最小 speedup 2.84（tn 64³），
即 **通用 hgemm 内核在全部 core shapes 上均已大幅快于该 DTK 唯一可用的原生 fp16 hipBLAS 入口**。

## 2. 结论与建议

1. **无需为满足“≥0.95 相对 baseline”而新增 hygon 专用 hgemm 内核**：通用内核（fp32 累加，
   cuBLAS gemmEx 语义）在所有形状上已达到 2.8–15.7x（中位 6.7–10.6x），远高于目标阈值。
2. **绝对吞吐仍有布局间差距（可选优化方向）**：大 shape（8192³）实测 FlagBLAS 吞吐约
   nn 105 / tn 62 / nt 154 / tt 76 TFLOPS（fp32 累加口径）。tn/tt 明显落后于 nn/nt，
   目前 hgemm 在 hygon 侧无 tune 配置，回落使用 NVIDIA 缺省 YAML；后续如追求绝对吞吐，
   可先尝试给 hygon 增加 `hgemm_{tn,tt}` tune 配置，或按 `_hygon/ops/sgemm.py` 的结构
   单独实现 tn/tt 的 fp16 访问优化内核。
3. hipBLAS-H 基线本身为 legacy `hipblasHgemm`（DTK 上 fp16 `gemmEx` 不受支持，见 §3），
   其吞吐仅 ~5–13 TFLOPS 且非 fp32 累加，因此“加速比”数值偏大属预期，需结合绝对吞吐解读。

## 3. 方法学说明（fp16 特有）

- DTK 25.04 的 `hipblasGemmEx`/`GemmEx_v2` 对 fp16（`HIP_R_16F` + `COMPUTE_32F`）一律返回
  status 10/7（NOT_SUPPORTED/INVALID），实测唯一可用入口为 legacy `hipblasHgemm`，
  故 latency baseline 用 `hipblasHgemm`（标量需按 fp16 `hipblasHalf` 打包）。
- `hipblasHgemm` 内部以低精度累加：实测 K=28672 时其 fp16 输出与 fp32 累加结果偏差达数十
  （11.7M 元素相对误差超 1e-2），不能作为 fp32 累加实现的精度参照。FlagBLAS 通用 hgemm 内核
  `tl.dot(..., out_dtype=fp32)` 与 NVIDIA cuBLAS fp16 gemmEx（fp16 入出、fp32 累加）语义一致，
  因此精度校验改为与 on-device torch fp32 matmul（fp16→fp32 无损）对比后再回投 fp16
  （`benchmark.gemm_perf_common.hgemm_reference`）。
- 独立进程复测（4096³/8192³，do_bench warmup=200/rep=50）与 pytest 记录数值偏差 <10%，
  排除此前“单进程长循环时间恒定”的运行时假象。
