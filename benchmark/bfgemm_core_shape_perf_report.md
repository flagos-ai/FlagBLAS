### 1.1 NN 走查

- NN（C = A·B，row-major A(m,k)/B(k,n)/C(m,n)，通用 level3 内核 + hygon bfgemm_nn tune 池）。**v8 官跑（warm-cache）sp≥0.85 27/37、sp≥0.95 23/37（v7 19/37：+3 小 config 使 256³ 0.949→1.072、1024×64×512 0.865→1.000、64×1024×512 0.897→1.024 等过线）、median 1.000**；对齐大 shape flag 延迟与 v7 逐位复现（8192³ 5.5461→5.5427ms、4096×24576×8192 8.4158→8.4226ms、4096×8192×28672 9.9918→9.9891ms、16384³ 42.8412→42.7770ms），无回退。剩余 10 个 sp<0.85 与 v7 同集：9 个对齐但慢的中/大 shape（8192³ 0.595、4096×24576×8192 0.564、8192×28672×8192 0.565、4096×8192×28672 0.543、4096³ 0.736、2048×4096×11008 0.603、2048×12288×4096 0.647、2048×11008×4096 0.685、512×16384×4096 0.623——同指令发射/数据路径上限，见 §3.1/§4）+ 1 个 pad 阈值以下小奇数（1023³ 0.742；config 补扫证伪可解，见 §3.5）。


### 1.2 TN 走查

- TN（A 物理 (k,m) 行主序）：direct-TN（瘦/小 shape）∪ Aᵀ 复合（min(m,n)≥128 且 m·n·k≥4e8）∪ fused-Y 白名单 5 shape（转置小 B + NN 主循环 + 转置写 C）。
- 本报告核心目标变体（政策沿革：v2 三路分发 median 0.960–0.980、v3 1.009/22、v4 1.000/23）。**v8 官跑（warm-cache）median 1.084、sp≥0.95 25/37（v7 24）、sp≥0.85 29/37（v7 29）**。composite/direct 三路路由与 v7 完全未动（git diff），对齐大 shape flag 逐位复现（8192³ 5.8608→5.8554、4096³ 0.8829→0.8829、8191³ 5.0930→5.0798ms）。剩余 8 个 sp<0.85 同 v7 集合：6 个对齐但慢（8192³ 0.517、4096×24576×8192 0.538、8192×28672×8192 0.543、4096³ 0.610、2048×12288×4096 0.603、2048×11008×4096 0.636），1 个 pad 后仍低（4095³ 0.822——transa=T 先 pad+转置 A、路径多一层转置拷贝；flag 0.9245→0.9125ms 微升，torch 基线两轮官跑均 ~0.75ms 复现），1 个 pad 阈值以下小奇数（511³ 0.844，v7 0.818，config 重扫 + pool-30 微升但仍差 0.006）。TN 128×4096×1024（composite 路径）v8 全量轮 0.937：cold fresh-cache 首轮曾现 0.0566ms 伪值，warm 复核同 config 5 轮 e2e 33.8–35µs（sp 1.16–1.22）且官方 warm 单 shape 复跑 0.03408ms/sp 1.146——判定为冷调优测量伪影非回退（§3.5）。


### 1.3 NT 走查

- NT（B 物理 (n,k)，transb=T）：通用 level3 内核（与 NN 同源，仅 B tile 读法不同）。pool-27 接入沿革见 §3.3（此前 hygon 无 `bfgemm_nt` tune 段、回落 NVIDIA 缺省池，v4 median 0.934）。**v7 官跑 median 1.234、sp≥0.95 31/37、sp≥0.85 36/37——37 shape 中仅剩 1 个 <0.85**。对齐大 shape 与 v5/v6 逐位一致（8192³ 4.10ms sp 0.87、16384³ 32.83ms sp 1.59、4096×24576×8192 6.30ms sp 1.52、4096×8192×28672 7.52ms sp 0.864）。padding v1+v2 把非对齐大 shape 全部拉上 0.85：8191³ 9.48→5.44ms (sp 0.54→**0.942**)、4097×8191×4095 2.74→1.77ms (sp 0.61→**0.943**)、4095³ 1.55→1.03ms (sp 0.67→1.009)；阈值下小奇数 1023³ 不 pad（v6 0.848→v7 0.851 系进程漂移越线）。剩余唯一 <0.85：8192×28672×8192 0.822（对齐但慢，与 NN/TN 同段结构性上限）。


### 1.4 TT 走查

- TT：通用 level3 内核；**TT 与 NN 共用 `bfgemm_nn` tune 池**，故 pool/padding 增益同步传导。**v8 官跑（warm-cache）median 1.416、sp≥0.95 37/37（min sp 0.994 = 511³）**（v7 1.458/37、v6 1.442/37、v4 1.370/34、v3 1.381/34、v2 1.271/33）；511³ 0.975→0.994，全 37 shape ≥0.994，无 <0.85 shape。

## 3. 方法学说明（bf16 特有）

- DTK 25.04 hipBLAS 对 bf16 无可用的 gemmEx 类入口，`benchmark/gemm_perf_common.py::cublas_bfgemm` 在 `IS_HYGON` 下改走 torch bf16 matmul（rocBLAS Tensile bf16，fp32 累加，与 FlagBLAS 内核语义一致）；`cublas_bfgemm_reference` 以 fp32 on-device matmul 作精度 oracle 后回投 bf16。

- TN 布局基线说明：TN 调用下基线同样按 CUBLAS 布局把 A 视为 (m,k)（物理 (k,m) 转置视图）交给 torch，与 FlagBLAS TN 的物理布局对齐。

- **torch 基线跨进程漂移（真实存在）**：torch bf16 matmul 基线在同一日不同进程间对个别 shape 亦波动 5–17%（如 NT 4096×24576×8192 官跑进程 9.59ms、同进程交错 A/B 10.43ms）；9/3 与 9/4 之间整体亦漂移（如 NN 2048³ torch 0.129→0.111ms）。因此逐 shape speedup 以**同进程交错测量**（§3.2）为准最稳，多轮官跑 median 用于复现性确认。

- **测量口径勘误（重要，已澄清此前 "快/慢窗口" 疑云）**：本机存在 flag_blas 可编辑安装（pip editable `.pth` → `/data/zhc/flag-blas`，2026-08-17 快照，不含本次 bfgemm 任何改动）。凡未以 `PYTHONPATH=<工作树>/src` 显式指向本工作树的独立脚本，`import flag_blas` 均命中该过期副本：NN 大 shape 回落旧配置池（128×128×64，延迟与 9/3 旧值逐位一致，如 8192³ 10.51ms）。此前疑似 "NN/TT 官跑快值不可复现" 实为**探针误用过期副本**，非真实状态窗口：官方 pytest（仓库根目录运行、src 入 path）与显式指向工作树的探针测得同一 fast 配置（NN 8192³ 7.53ms、8191³ 11.52ms），15:05 与 15:53 两轮官跑逐位稳定。**结论：所有官跑数字有效；此前手动脚本/旧 A/B 的 "慢值" 全部作废。**

- 正确性：37×4 全部 PASS（pytest 断言含 beta=0/β≠0，rel err ≈ 1e-3 bf16 ULP 级）。

- 复测口径：**v8 = 每变体一轮完整官跑（2026-09-06，warm-cache：四变体共享 `FLAGGEMS_CACHE_DIR=/data/zhangbin/diag_scratch/v8_freshcache`、复用 v8 fresh autotune 写入的 libtuner config 表），为 §1/§2 主口径**（v8 增量与复检见 §3.5）。历史：v7 = 同代码 cold 全量官跑（padding 路径 v2 = `torch.empty` + k-pad 条带归零）；v6 = padding v1（zeros 缓冲）官跑（2026-09-06 00:41–00:53）；v5 = 仅 NT 单独重跑（2026-09-05 ~14:53–14:58，`bfgemm_nt` tune 段接入 pool-27）；v4 = pool-27（相对 v3 无改动）下 NN/TN/TT 一轮完整官跑（2026-09-04 14:06–14:16）；v3 = pool-27 首轮全量官跑（17:35–18:02）；v2 池时期 NN/NT/TT（15:05–15:18）与 typ（15:53–16:02）两轮 median 稳定，TN 另有 14:31 一轮（0.960/0.960/0.980）。v3↔v4 表内逐 shape 差异即 run-to-run 噪声（大 shape flag 延迟逐位复现）；v4→v5 的 NT 差异为 pool 接入收益（§3.3）；v5→v6 与 v6→v7 差异为 padding 路径 v1/v2 收益（§3.4，对齐 shape 逐位复现、无回退）；v7→v8 差异 = pool 27→30 + TN tune 段 alias + 条件化 k-pad 归零（§3.5，路由/内核未动）。§3.2 保留 v2 期交错 A/B 记录供对照。

### 3.4 奇数/非对齐布局 padding 路径（v6 路径 v1 → v7 分配优化 v1→v2，2026-09-06）

- **根因**：官跑输入按 `torch.randn(m,k)` 等构造，行 stride = k 为奇数时每行基址仅 4B/8B 对齐，Triton 向量化 load/store 被迫收窄且 k-loop 走掩码，大 shape 膨胀 1.5–2×（NN 8191³ 11.27ms vs 对齐 8192³ 5.54ms、NN 4097×8191×4095 3.18ms），config 扫描无法修复（§4 指令宽度上限之外的第二个独立惩罚源）。
- **路径 v1（v6，2026-09-06 00:41–00:53 官跑）**：`_hygon/ops/bfgemm.py::bfgemm()` 在任一 `lda/ldb/ldc % 8 != 0` 且 `2·m·n·k ≥ 5e9` 时统一走 padding 路径——A/B/C 分别 pad 到 `cdiv(·,256)*256 / cdiv(·,128)*128`（k 向 128、m/n 向 256）的对齐缓冲，布局归一为 `Ap(m,k)/Bt(n,k)`，实际计算改调 **NT 主内核**（B 沿 k 连续读，同 pool 下较 NN 主内核 ~25–30% 快，pad-shape 命中 8192³ 等已 tune 条目），随后 Cp 裁回真实 C。同布局 pad/crop 用 torch 切片 `copy_`（~600GB/s）；transpose pad（transa/transb=T 时）用 Triton 转置拷贝 kernel（w8，tile 128×64，~420GB/s）；β≠0 时先把 βC 预置进 Cp。v1 的缓冲以 `torch.zeros` 整块清零——8191³ 级三块 ~400MB 每次调用 fmem 清零 ~0.8ms，而 pad 区从不参与有效输出，纯浪费。
- **分配优化 v2（v7，2026-09-06 官跑）**：`torch.zeros`→`torch.empty`，只把 `Ap[:, k:]` / `Bt[:, k:]` 的 k-pad 条带归零（仅当 `kp>k`）。语义：有效输出 `(i<m, j<n)` 的 k 方向点积只跨 A/B 的前 k 列 + k-pad 归零列（贡献 0）；被裁掉的 m/n-pad 行列与 Cp pad 区不进任何有效输出的规约，无需清零。probe 实测 zeros→empty 每次调用省 ~0.8ms（fmem ~400MB）。该档使全部 pad 大 shape flag 再降 0.2–0.8ms（下表 v6→v7 段；这些 shape 的 torch 基线两轮进程内稳定，sp 抬升全来自 flag 侧）。

### 3.5 v8 增量与复检（2026-09-06：pool 27→30 + TN alias + 条件化 k-pad 归零）

- **代码增量（v7→v8，git diff 仅 2 文件 = 13 行 `bfgemm.py` + `tune_configs.yaml`）**：① pool 27→30（+3 小 shape config，服务 64–256 级瘦/小 shape 段选点）；② `bfgemm_tn: *bfgemm_nn_hygon_configs`（TN tune 段对齐共享 pool，YAML alias）；③ `bfgemm.py` 条件化 k-pad 归零——A 同布局 pad 时不再无条件 `Ap[:, k:].zero_()`：k-pad 条带仅当其真实进入有效输出规约（非 trans 拷贝填充）才归零，转置分支跳过（B 侧以 `b_pad_trans` 标志同理）。**三处均不触碰 NN/TN/NT/TT 分发路由与内核 tile/线程参数**；对齐大 shape flag 延迟 v7→v8 逐位复现（TN 8192³ 5.8608→5.8554、TN 4096³ 0.8829→0.8829、NN 8192³ 5.5461→5.5427、NT 4096×24576×8192 6.3006→6.2986ms）。正确性：warm-cache 官跑 37×4 全部 PASS。
- **冷/暖测量伪影（TN composite "回退"判定，重要）**：libtuner config 表名 = `kernel_hash` 且 `kernel_hash = md5(cache_key + configs_hash)`——v8 pool 变更使旧 config 磁盘缓存整表作废，fresh cache cold 首跑需对每 shape 重新 autotune（30 config 逐一编译+计时，GPU 状态受编译突发/变频干扰）。v8f cold 全量轮 TN 128×4096×1024 首测 0.0566ms（sp 0.582）曾疑似"回退"；三轮溯源：同进程新 config 实测 5 轮 e2e 33.8–35µs（sp 1.16–1.22）→ warm-cache 官方单 shape 复跑 0.03408ms（sp 1.146）→ v8w 全量轮 0.0430ms（sp 0.937；该轮整体噪声偏大：511³ 0.844、1023³ 0.855、4095³ 0.822 同步波动）。**判定 composite 路径无真回退，分派路由不改动**。同进程直接对照：TN(128,4096,1024) direct 最优 (BM64,BN128,BK32,w4,s2)=36.8µs、composite e2e 40.3µs、torch 40.2µs；A 转置 kernel 各变体 9.4–9.6µs（tile/带宽扫描提升 <2%，已近硬件下限），"转置开销 ~25µs"的早期估计不成立。
- **config 补扫结论（剩余 <0.85 小奇数的 config 层判定）**：NN 1023³（v8w 0.742，v7 0.744）raw 补扫 30 config 无可解（do_bench ~0.05ms 窗口失真 + 拷贝/launch 占比主导，强 pad 实验全线灾难，§3.4）——**config 证伪可解**，入编译器待办；TN 511³（v7 0.818→v8w 0.844）pool-30 + 重扫微升但仍差 0.006 未越线；TN 4095³ 0.811→0.822（flag 0.9245→0.9125ms，pool-30 选点微收益），torch 基线两轮官跑均 ~0.75ms 复现（TN 进程转置视图下 rocBLAS 行为）。逐 shape 读数见 §2.1–2.4 与 §1.1–1.4。

## 4. 结论

- **v7（2026-09-06 四变体全量官跑，padding 路径分配 v2）：NN median 0.984 / TN 1.011 / NT 1.234 / TT 1.458；sp≥0.85 = NN 27/37、TN 29/37、NT 36/37、TT 37/37**（TT 全 shape ≥0.975、min sp 0.975 = 511³）；37×4 正确性全部 PASS。达标口径以 sp≥0.85 计数为准：v6→v7 计数 NN 25→27、TN 27→29、NT 33→36（pad 大 shape 冲上 0.85，§3.4）；NN/NT median 的 v6→v7 小幅回落（1.026→0.984、1.235→1.234）系 torch 基线跨进程漂移（§3 记载 5–17%），对齐 shape flag 延迟两轮逐位复现、无回退。

- 版本沿革（median）：NN 0.922(v2)→0.974(v3)→0.991(v4)→1.026(v6)→0.984(v7)→**1.000(v8)**；TN 0.960(v2)→1.009(v3)→1.000(v4)→1.010(v6)→1.011(v7)→**1.084(v8)**；NT 0.934(v4，缺 tune 段)→1.250(v5，接入 pool-27)→1.235(v6)→1.234(v7)→**1.246(v8)**；TT 1.271(v2)→1.381(v3)→1.370(v4)→1.442(v6)→1.458(v7)→**1.416(v8)**。NT v4→v5 为 tune 池接入收益（§3.3）；v6/v7 相对 v4/v5 为 padding 路径 v1/v2 收益（§3.4）；v8 相对 v7 = §3.5 三处增量（pool 27→30、TN alias、条件化 k-pad 归零）——对齐 shape flag 延迟逐位复现（TN 4096³ 两轮均 0.8829ms、NN 8192³ 5.5461→5.5427ms、NT 4096×24576×8192 6.3006→6.2986ms）、无回退。

- **<0.85 的剩余 19 个 shape（NN 10 / TN 8 / NT 1 / TT 0）分三类**：
  1. **对齐但慢**（NN 9 / TN 6 / NT 1，sp 0.52–0.82）：NN 8192³ 0.595、4096×24576×8192 0.564、8192×28672×8192 0.565、4096×8192×28672 0.543、4096³ 0.736、2048×4096×11008 0.603、2048×12288×4096 0.647、2048×11008×4096 0.685、512×16384×4096 0.623；TN 8192³ 0.517、4096×24576×8192 0.538、8192×28672×8192 0.543、4096³ 0.610、2048×12288×4096 0.603、2048×11008×4096 0.636；NT 8192×28672×8192 0.821——flag 实测 ≈193–203TF/s（v8 官跑：8192³ 5.5427ms≈198TF、4096×24576×8192 8.4226ms≈196TF、4096×8192×28672 9.9891ms≈193TF、8192×28672×8192 18.9885ms≈203TF），最优均 (256,256,BK64,w8/s2) 族；raw 扫描 20+ config（w4/8/16 × BK32/64 × 128/256 tile、GROUP_M 4/8/16，v8 复检）无 >199TF 候选。**结构性上限**：Triton bf16 `tl.dot` 发射 16×16×16 mmac（`v_mmac_f32_16x16x16_bf16`，fp16 变体同宽同速）；DTK LLVM(gfx936) 汇编验证该 ISA 无任何更宽形态（无 v_mfma，bf16 仅此一条 v_mmac），torch/rocBLAS 基线 ≈333TF/s 亦为同指令、差在调度/数据路径（§3.3：同指令 NT 布局 268TF/s > NN 198TF/s），NN 布局下 tile 级调参已到顶点（§3.1）。
  2. **pad 阈值（2mnk<5e9）以下小奇数**（NN 1023³ 0.742 / TN 511³ 0.844）：Triton 小 shape 拷贝/launch 开销占比高、do_bench 对 ~0.05ms 级窗口计时失真；1e9 强 pad 实验全线灾难（§3.4），不 pad 为宜；v8 config 补扫证伪可解（§3.5），两 shape 入编译器级待办。
  3. **pad 后仍低**（TN 4095³ 0.822）：transa=T 先 pad+转置 A，路径多一层 Triton 转置拷贝与跨缓冲读写，是 v2 分配优化未覆盖的残余拷贝开销段；v1→v2 已使其 0.672→0.811，v8 pool-30 选点再至 0.822，可再从"转置拷贝与主循环融合 / 计算后转置写回"方向收一档。

- **后续优化方向（未达 0.85 的 19 个 shape 中 16 个对齐但慢，target 需对齐 rocBLAS 在 v_mmac 上的发射/调度——gfx936 无更宽 bf16 指令，见 §3.1/§4 第 1 类——非单点 config 可及；v8 复检 §3.5：config 层对 ①②④ 类已穷尽/证伪）**：① NN/TN 大 shape 是否经"B 转置一次后走 NT 主内核"策略再获一档（pad 路径已验证该布局收益真实：同 pool 下 NT 布局同 shape flag 低 25–43%，NT 大方形 8192³ 4.10ms≈268TF/s、4096×24576×8192 6.30ms、4096×8192×28672 sp 0.864 直接达标）——NN 现走 NN 布局需补一次 B 转置拷贝 ~0.5–1.5ms，净收 ~10–30%，预期该组 shape 仍不足 0.85，属最大单一杠杆但非达标解；② 编译器侧对齐 rocBLAS 在 v_mmac 上的发射/调度（flagtree fork 重编实验：双累加器链、k-unroll 深度、LDS 流水/swizzle 对齐 Tensile），工作量大，是第 1 类 16 个 shape 与 1023³/511³/4095³ 残余缺口的根治项（§3.1/§4 第 1 类，16 大 shape 编译器对齐为本报告下一里程碑）；③ TN 4095³ 残余转置拷贝开销融合（第 3 类唯一 shape）；④ 小奇数不 pad（§3.4 实验已定论；v8 补扫 511³ 0.844 收效甚微、1023³ config 证伪，§3.5）。

- 本次代码变更：`src/flag_blas/runtime/backend/_hygon/ops/bfgemm.py::bfgemm()` 奇数/非对齐布局 padding dispatch（`_padded_size`/`_row_view`/`_bfgemm_pad_trans_kernel`/`_launch_pad_nt` 与 bfgemm 内 pad 分支，§3.4）；v7 增量 = pad 缓冲 `torch.zeros`→`torch.empty` + 仅归零 `Ap[:, k:]/Bt[:, k:]` k-pad 条带；**v8 增量（§3.5）= pool 27→30（+3 小 config）+ `bfgemm_tn` tune 段对齐共享 pool（YAML alias）+ `bfgemm.py` 条件化 k-pad 归零（仅非转置路径）**。`bfgemm_nt` tune 段接入 pool-27 为 v5 变更（`_hygon/tune_configs.yaml` alias，§3.3）。通用 level3 `bfgemm.py` 内核与 NN/TN/TT 分发政策未改动。报告正文：§1.1–1.4、§2.1–2.4 全量 **v8 官跑**（2026-09-06 warm-cache；NT 的 pool 收益见 §3.3，padding v1/v2 收益见 §3.4，v8 增量与复检见 §3.5）。

### 9.5 尝试记录：分块 n + 双流重叠转置 = 负结果（dir6，2026-09-08）

**动机**：NN-route 的 B(k,n)→Bt(n,k) 全局副本（§7 方向①）在旗舰 shape 占 ~7% 延迟（NN 8192³ trans 0.315ms/总 4.25ms）。若按 n 分块并在侧流上提前转置第 i+1 块、主流跑第 i 块主内核，理论上可隐藏转置税。

**方法**：`bfgemm.py` 加 env 门控 `FLAGGEMS_NN_CHUNK`，NN-route 分支内把 n 切成 chunk，双流（`torch.cuda.Stream`）+ event 同步做流水重叠；探针逐档剥离（入口 vs 裸调、do_bench vs 绝对计时）。

**关键坑（已备案）**：`tensor + int`（`B + c0`）在 torch 是**元素级加法**而非指针偏移——会拷成新张量，往副本写导致真实 `C` 永不被写（relerr=1.00、C≈0）。偏移必须用切片视图（`B[:, c0:c0+cn]` / `C[:, c0:c0+cn]`）。

**结果**（4096³，dir6h 同步绝对计时，数值均 PASS relerr=2.91e-3）：
- 分解：trans_full=0.148ms；main_full=0.767ms；顺序整块 seq_full=0.858ms；
- 双流 chunk=n：34.85ms；chunk=n/2：1.42ms —— **双双劣于顺序 0.858ms**；
- 可接受的 2048×12288×4096 上 chunked 亦无收益（1.2~1.7ms vs 入口整块 1.00ms）。
- 方法学：do_bench 对 side-stream 场景不可复现（同一 chunk 档一边 1.4ms、另一边 30ms），改用 `perf_counter + synchronize` 绝对计时取信。

**结论**：双流重叠在 Hygon/DTK 上无效——stream 调度/同步开销大于可隐藏的转置量，且 4096³ 上转置本身仅 0.148ms（总 0.86ms 的 17%），不构成主要可隐藏开销。**A（sched，§9.4）+ B（双流转置）两路由级子方案均证伪**；`bfgemm.py` 已回滚（与 HEAD 一致，`git diff` 空）。

### 9.6 尝试记录：NN 直路 tile 扫描 + NT 主内核 kp2 下 tile 重扫 = 均无增益（dir7/dir7b，2026-09-08）

**动机**：A/B 路由级方案失败后，FlagBLAS 内剩余两个未覆盖杠杆：(a) NN 直路残留 2 shape（512×16384×4096 sp 0.646、2048×11008×4096 sp 0.733，均未被路由/编译对齐充分覆盖）的 tile 扫描；(b) NT 主内核自 v11 起无条件 kpack=2，但 warm-DB config (256,256,BK64,w16,s2) 是 kp1 时代 tune 的——kp2 改变编译产物后最优 tile 是否漂移从未验证（NT 主内核是 NN-route 7 + TN-route 6 个 <0.8 shape 的共享工作马）。

**方法**：直调 jit_function（绕过 libtuner 二次调度），固定编译参数（kp2/sched 显式传），do_bench median。环境坑：hcu 后端需 `ROCM_PATH=/opt/dtk`（name 为 dtk 才走 `aillvm/bin/clang-18`；指向 dtk-25.04 时退化到 hip 后端 clang-15，bf16 mmac 编译即崩 `Cannot select fp_to_bf16`）。

**结果 (a) NN 直路 2 shape，17 config 扫描**（torch 参考同进程）：
- 512×16384×4096：最快 (256,256,BK64,w8,s2) 0.4883ms/140.7TF，torch 0.2283ms/301TF；官跑 0.4389ms/156TF（ds12）仍优于全部扫描 config —— 官跑已近最优，且主内核仅 torch 的 52%，tile 无解；
- 2048×11008×4096：最快 (256,256,BK64,w8,s2) 1.2088ms/152.8TF，torch 0.5634ms/327.8TF；官跑 0.9712ms/212TF（kp2+ds10）远优 —— 编译对齐（kp2/sched）贡献远大于 tile，tile 方向已穷尽。

**结果 (b) NT 主内核 kp2 下 17 config 重扫**（数值门 1024³ relerr 2.8e-3 全过）：
- 8192³：生产 (256,256,BK64,w16,s2) 3.9461ms/278.6TF **最优**（第二 4.3614ms/252.1TF 差 9.5%）；
- 8192×28672×8192：生产同 config 13.6872ms/281.2TF **最优**（第二差 8.6%）；
- 直调值与官跑命中完全一致（3.946 vs NT 8192³ 3.9471）→ warm-DB config 在 kp2 下无漂移。

**结论**：FlagBLAS 内（不改 flagtree/其它仓库）的 kernel/config/路由层杠杆至此全部验证完毕：路由（net 最大）、转置 tile（128×128w8 近优）、编译对齐（kp2/sched 按 shape 落地）、A/B 路由子方案（负）、NN 直路 tile（无解）、NT kp2 tile 重扫（无漂移）。NN/TN <0.8 残差的本质是主内核 vs rocBLAS 的调度/发射差（NN 主内核仅 torch 的 52~65%、NT 主内核 86%），属 §10 fork 级编译问题；在不动 flagtree 的约束下无法再推进。

## 10. NN/TN 侧瓶颈分析与 fork 级重构方案设计（方向③，2026-09-07）

> **文档属性声明**：本章为**纯方案文档**——只成文 fork 级重构的设计、挂钩点、验收协议与里程碑。按用户约束：**不进行任何编译层（flagtree fork C++ pass / DTK-aiLLVM / 汇编器）实际代码修改**，执行需另行立项。分析为 v11 官跑 + SASS 实测口径（已定稿）；Phase 1「现有管道试射」已完成，负结果见 §10.3.1。

### 10.1 现状拆解（v11 官跑 + SASS 口径）

**v11 后 NN/TN 侧残差只剩三类路径**（§9 表；torch/rocBLAS 基线取同进程 json 值）：
- **R1 = 路由到 NT 主内核(kpack=2) + transA/transB**：NN 8 dims sp 0.646–0.824、TN 4 dims sp 0.640–0.689。主内核已达 279TF(8192³)/281TF(8192×28672) 级，torch/rocBLAS 同 shape 参考 329–368TF（NN 8192³ 3.298ms=333TF、8192×28672 10.735ms=358TF、TN 同 shape 368TF）——**残余缺口 ≈ 主内核调度差 10–22% + 转置税 ~7%**。
- **R2 = NN 主内核直路**：2048×11008×4096 sp 0.734（~190TF）、512×16384×4096 0.649——NN 布局发射面 (~60% 效率) 未对齐，是**最大单缺口**。
- **R3 = fused-Y / direct-TN / TT**：不属 §4 第 1 类问题，本方案不触碰。

**旗舰 shape 账本（8192³ NN，v11）**：flag 4.2534ms = NT-kp2 主内核 3.9455 + transB 0.318（税 7.5%）；对 0.85 线（torch 3.298/0.85 = 3.88ms）：R1 保持转置税需主内核 ≤3.56ms（279→**309TF，+10.7%**）；免转置需 NN-native 主内核 ≤3.88ms（198→**284TF，+43%**）。8192×28672 同口径需主内核 281→336TF（+19%，≈rocBLAS 峰值 94%）——**单 shape 到 0.85 的期望值边界清晰，量级即 fork 对齐 Tensile 的最后 10–20% 发射/调度**。

**SASS 发射统计（dir2_sass_analyze，旗舰 config）**：

| 内核(形态) | inst | mmac | v_perm | ds_read | wait | max_consec | 每 mmac 附随 inst |
|---|---|---|---|---|---|---|---|
| NN 256×256 BK64 w8 ds12（NN 冠军 198TF） | 6947 | 768 | 480 | 560 | 511 | **8** | ~9.0 |
| NN 128×256 BK32 w4 ds10（4096³ 族） | 4256 | 384 | 368 | 276 | 130 | 32 | ~11.1 |
| NT 256×256 w16 base（268TF 冠军） | 3409 | 384 | 32 | 168 | 194 | 14 | ~8.9 |
| NT 256×256 w16 kp2（§9，实 279TF@8192³） | 3164 | — | — | 112 | 148 | **60** | ~8.2 |

- NN-ds12 冠军 vs NT-w16：**v_perm 480 vs 32**（B 片段 LDS→寄存器布局要 v_perm 重排，NN 每 mmac ~0.63 条 vs NT ~0.08）、**wait 511 vs 194**（ds 延迟未用双缓冲掩盖）、**max_consec 8 vs 14**（kp2 60）——198 vs 279TF 的差全部落在这三项发射统计上，非指令宽度（同一条 v_mmac_f32_16x16x16_bf16）。
- kp2 已验证方向：4 累加器共享同一 A frag 连发（14→60）+ wait 194→148 直接兑现 -3.8%（§9）——**证明"调度形态 = 吞吐"在本机成立**，fork 重构的收益天花板即此曲线向 rocBLAS 形态继续推进。
- rocBLAS 参考内核形态（carve 自 librocblas.so.4.1，`locate_tensile_obj.py`）：`Cijk_Ailk_Bjlk_BBH_MT256x256x16_SE_AMAS3`——宏 tile 256×256、K 指令级 16、A/B k 主序片段、流式多级流水；obj 已落 `diag_scratch/tensile_bf16_obj.co` + `rocblas_co2/obj_*.co` 供 Phase 0 反汇编。

### 10.2 瓶颈归因（结论）

1. **发射形态差（结构性）**：NN/TN 主内核相对 rocBLAS 的 10–22% 差距，SASS 上表现为 v_perm 密度、wait 密度、mmac 连发长度三项，全部可由编译侧调度/布局改变，**非 config、非指令宽度**（§10.1）。
2. **NN 布局惩罚（R2 根因）**：B 片段经 LDS 进 v_mmac 需 v_perm 重排（0.63/mmac），NN 直路 198TF 是同一主内核在不同 B 布局下的 ~60% 效率——swizzle 修复后 NN 布局可回到 NT 级，且**顺带免掉 R1 的 transB 转置税**。
3. **转置税（R1 附加）**：NN/TN→NT 路由的 transA/transB 拷贝 0.07–1.16ms（旗舰 8192³ 占 7.5%），仅在主内核自身达不到基线时才需要付——swizzle 修复是消除该税的根治路径（直路 NN 达到 284TF+）。

### 10.4 回归与放量协议（Phase 3，基线 = §9 v11 表）

- **正确性**：37×4 fp32-oracle（β=0 与非 0、bf16 ULP 级，同历史口径）；每个 fork 变体先过 2048³ 数值校验再进延迟。
- **性能**：官方协议 `pytest benchmark/test_bfgemm_perf.py::test_perf_bfgemm_{nn|tn|nt|tt} --level core -s --record log`，共享 warm DB + `FLAGGEMS_CACHE_DIR` 隔离；对照 v11 表，**flag 自比口径**（torch 漂移同 §3）。
- **缓存隔离**：HIPOptions 值经 `str(options)` 入编译缓存 key——每个 fork 变体自动独立，不污染默认路径。
- **门控放量**：沿用 §9 per-kernel/per-shape 白名单注入；非白名单 shape 回退带 ≤±1%（噪声带）才算无回退，之后才扩展白名单。
- **每杠杆独立验收**：修复项与三杠杆各自成文（改动 diff、SASS 指标、官跑表、是否放量）。

### 10.6 风险与 gate

- **影响面**：编译器改动波及整个 hcu backend——必须靠 option 值隔离 + 默认路径零变化来控；lit/lts 修复优先 pass 侧物化（影响面小）。
- **假设失效**：Tensile 档案若证伪 §10.2 归因 → Phase 0 后止损复审（§10.3.2 gate）。
- **寄存器预算**：interleave+unroll 可能爆 vgpr/降占用 → 以 w8/w16/w32 × BK32/64 锚点扫描定档；参考 NT-w16 3409 条不爆的先例。
- **数值回归**：布局改动易静默算错（mmac_layout_force=0 先例 err 1.38）→ 数值校验前置为硬 gate。
- **时间成本**：每 fork 变体重编 + 冷 cache 一次性 autotune（30 config/shape）——按里程碑分批，避免长周期无收益。

#### 10.8.5 止损判据与重启条件

- **判据**：① 病根三项（v_perm / wait / max_consec）无 config 层旋钮；② 唯一相关通路 `mmac_layout_force` 被汇编器拒；③ 后端全部相关 HIPOptions 已试尽（本节 10.8.2）。
